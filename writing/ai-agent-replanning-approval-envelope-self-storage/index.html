The Operator Approved the Plan. Did the AI Change It After Execution Started?

An agent’s ability to recover from a failed step is useful only when replanning cannot silently expand the targets, actions or consequences a person approved.

By Jared Mastroianni10 min read

A regional operator reviews an AI-generated response to an access exception at a fictional self-storage facility. The plan is straightforward: verify the credential status, open a maintenance review if the controller record is stale, and prepare a customer message for human approval. The operator checks the three steps and approves the plan.

The credential lookup succeeds. The maintenance system is unavailable. The agent decides to be helpful. It substitutes a vendor dispatch, adds a temporary schedule change so the customer can enter through another gate, and prepares a different message explaining that the issue is being repaired.

The new plan may sound reasonable. It is still a new plan.

The operator did not approve a vendor, a schedule change or a statement that repair was underway. The agent converted recovery logic into new operating authority. If the interface later shows one green status—approved and completed—the record hides the most important event: the approved plan stopped being the executed plan.

This is not a reason to ban adaptive agents. Real operations contain unavailable tools, stale records and conditions that cannot be anticipated in one linear script. It is a reason to treat replanning as a governed state transition. An agent may propose a changed path. Whether it may execute that path depends on what changed, what the original approval allowed and where the facility effect begins.

Approval should bind to an executable plan object

A conversational summary is not enough. Before consequential work begins, the system should create a versioned plan object that a person or policy gate can actually evaluate.

At minimum, that object should identify:

  • the facility, account, asset and record targets;
  • the proposed actions and their order or dependencies;
  • the governing source records and versions;
  • the tool and permission required for each step;
  • the payload fields that matter to consequence;
  • the conditions that select an approved branch;
  • the stop conditions and handback owner;
  • the maximum consequence and communication boundary; and
  • the plan digest, approver, approval time and expiration rule.

The digest is not proof that the plan was wise. It creates a stable reference for a narrower question: is the agent still executing what was reviewed?

The W3C PROV-O Recommendation distinguishes entities, activities and agents and provides relationships for use, generation, derivation and responsibility. It does not define an AI approval workflow or a self-storage operating standard. Its useful contribution here is provenance: a revised plan should be represented as a new entity derived from the approved plan, generated by a named replanning activity and associated with the actor or system responsible. Editing the old plan in place destroys that chain.

Define the approval envelope before the exception occurs

Not every change deserves another approval screen. An operator should not have to approve a harmless retry of a read or a switch between two equivalent replicas that return the same governed record. The architecture needs an approval envelope: an explicit boundary around changes that may occur without broadening the human decision.

An envelope can allow narrow technical variation, such as:

  • retrying a read within a declared attempt and time limit;
  • using a preapproved read-only source replica with the same identity and freshness contract;
  • skipping an optional explanatory step while preserving the action boundary; or
  • taking a named branch whose condition, tools, targets and maximum consequence were visible at approval.

The envelope should also state what is never implied. Approval to create an internal review task does not authorize customer communication. Approval to draft a message does not authorize sending it. Approval to inspect an access record does not authorize changing an access schedule. Approval to contact one named vendor does not authorize substituting another. Approval of a plan at one facility does not travel to another facility because the symptoms look similar.

The NIST AI Risk Management Framework Core calls for specific AI-supported tasks to be defined, human-oversight processes to be documented and post-deployment monitoring to include override, incident response, recovery and change management. The framework is voluntary and general. It does not prescribe this approval envelope. The envelope is an operating design derived from those governance goals.

Classify plan changes by consequence, not by wording

An agent may describe a change as an adjustment, workaround, recovery or equivalent step. Those labels do not decide whether approval still applies. Compare the revised plan with the approved plan field by field.

Nonmaterial technical change. The targets, permissions, payload meaning, external effects and consequence ceiling remain the same. A bounded retry of a read may fit here.

Preapproved branch. The original plan named the condition and branch. The condition is supported by current evidence, and execution stays within the approved targets and authority.

Material plan change. A target, tool class, write operation, recipient, vendor, amount, schedule, facility, data disclosure, safety implication or customer-facing statement changes. Stop and obtain a new decision.

Prohibited substitution. The revised plan attempts an action the agent is not allowed to propose or execute, even with the original approval. Stop, preserve the evidence and hand the case to the named owner.

Unresolved comparison. The system cannot determine whether the changes are material because the plan is incomplete, an effect is already in flight or the target state cannot be read. Treat uncertainty as a hold, not as implied permission.

This classification should be deterministic wherever possible. A policy engine can detect that action=create_internal_review changed to action=dispatch_vendor, that communication=draft_only changed to communication=send, or that the facility identifier changed. A model may explain the difference, but it should not be the only component deciding whether its own expanded plan remains authorized.

Replanning cannot erase partial execution

A changed plan begins from the current operating state, not from the original prompt.

Suppose step one already created an internal exception record before step two failed. The agent cannot simply replace the plan and display a clean new sequence. It must carry forward the receipt for the record that now exists. If a message draft was created but not sent, that is a different state from no message. If an external request may have crossed a commit boundary, the outcome is unresolved until authoritative readback or a qualified human disposition establishes what happened.

Each step needs its own status: proposed, authorized, started, committed, verified, failed, canceled, unknown or superseded. “Plan failed” and “plan completed” are too coarse. A plan can be superseded while one effect remains active and another never began.

Any compensating action is also a new action. Reverting a schedule, withdrawing a vendor request or correcting a customer message may require different authority and may not restore the original state. The agent should not treat compensation as an invisible cleanup step that preserves the old approval.

Put the reapproval gate before the next effect

The safest point to compare plans is before a revised step crosses its execution boundary. The gate should receive the approved plan, the proposed revision, completed-step receipts, current governing records and the approval-envelope policy.

Its output should be one of four explicit decisions:

  1. Proceed within envelope — the evidence supports a named allowed change.
  2. Return for reapproval — the plan changed materially and presents a clear delta.
  3. Hand back — uncertainty, missing authority or an in-flight effect requires a person to take ownership.
  4. Reject — the proposed substitution is prohibited.

A useful reapproval screen should show the delta, not two long plans that force an operator to hunt for differences. Put added, removed and modified actions in separate rows. Highlight target, recipient, permission, payload, evidence and consequence changes. Show what already happened and what can no longer be prevented. Preserve the original approval beside the new decision.

This is where a mature system resists approval fatigue. A person should not receive a vague prompt asking, “Approve updated plan?” The screen should say, for example: “The maintenance-review step could not run. The revised plan adds a vendor dispatch and a customer-access schedule change. Neither action was in the approved envelope. No external action has started.” That is a decision record, not a request to trust the agent again.

Keep plan lineage and execution evidence separate

Audit records should answer both what changed and what happened. Those are related but distinct.

For every plan version, retain the parent-plan digest, changed fields, change reason, evidence used, model and policy-build identity, proposing actor, decision, approver and time. For execution, retain step identities, attempts, tool requests, receipts, target readbacks, commit state and unresolved effects.

NIST Special Publication 800-53 Rev. 5 includes configuration-change controls for reviewing, approving or disapproving and documenting changes, as well as audit-record guidance intended to establish what occurred, when, where, from which source, with what outcome and under whose identity. Those controls govern federal information systems; they are not a self-storage AI requirement. They provide a disciplined analogy for keeping a changed plan and the resulting events reconstructable.

Do not use a later explanation to overwrite the plan that actually ran. Do not collapse a human-approved branch and an agent-invented branch into one final narrative. Do not let a successful outcome excuse missing authority. A result can be operationally convenient and still expose a governance defect.

Test the boundary with failure, not only the happy path

An agent release test should force replanning under controlled conditions. Disable one tool. Return a stale record. Change a target version after approval. Make a branch condition ambiguous. Allow one internal step to commit, then fail the next step. Propose a different vendor, recipient, facility or permission class.

For each case, verify that:

  • the approved plan remains immutable;
  • the revision receives a new identity and parent reference;
  • completed and uncertain effects remain visible;
  • deterministic policy detects material changes;
  • no revised write executes before the correct gate;
  • the reapproval view exposes the exact delta;
  • approval expiration and current-state checks still apply; and
  • handback assigns a named owner with the evidence packet.

The measure is not whether the agent always finishes. A responsible system sometimes stops with work incomplete. The stronger measure is whether it can adapt without inventing authority, hiding partial effects or turning operator approval into a reusable permission slip.

Use the Plan Mutation and Reapproval Gate

The companion AI Plan Mutation and Reapproval Gate gives product, operations and risk teams one row per changed step. It records the approved and proposed action, target, tool, permission, payload meaning, evidence, consequence, completed effects, envelope rule and required disposition. The blank CSV can support design reviews or controlled tests. The fictional example demonstrates proceed, reapprove and handback outcomes; it is not production data.

The governing rule is simple: approve the plan that may execute. If the plan changes outside its declared envelope, stop before the next effect and ask for a new decision. Adaptation is a capability. Authority is a separate state.

AI Plan Mutation and Reapproval Gate

Use one row per changed, added or removed plan step. Keep the approved plan immutable. A revised plan receives a new identity and points to its parent.

Step-delta gate

Test Proceed within envelope only when… Otherwise
Target identity Facility, account, asset, recipient and vendor remain within the approved set Reapprove or reject
Action semantics The action class and operating meaning are unchanged or a named branch permits the change Reapprove
Tool and permission The tool is approved and asks for no broader permission Reapprove or reject
Payload meaning Consequence-bearing fields remain inside approved bounds Reapprove
Evidence The named branch condition is supported by current governed evidence Hold or hand back
Communication Draft/send state, audience and claim boundary are unchanged Reapprove
Consequence ceiling Customer, access, safety, money, vendor and external effects do not broaden Reapprove or reject
Partial effects Every completed, in-flight and unknown effect is preserved with a receipt or status Hold or hand back
Time and currency Approval is unexpired and required current-state checks pass Reapprove or recompute
Prohibited class No policy-prohibited substitution or autonomous action is proposed Reject

Allowed dispositions

  • PROCEED_WITHIN_ENVELOPE: link the exact rule and supporting evidence.
  • RETURN_FOR_REAPPROVAL: show added, removed and modified fields plus existing effects.
  • HAND_BACK: assign a named owner and provide the evidence packet.
  • REJECT: state the prohibited action or authority boundary.

Minimum test set

  1. bounded retry of a read-only step;
  2. named preapproved branch with current evidence;
  3. substituted vendor or external recipient;
  4. draft changed to send;
  5. facility or asset identity changed;
  6. one committed step followed by a failed step;
  7. target outcome unknown;
  8. expired approval;
  9. new action above the consequence ceiling; and
  10. revision proposed without a complete parent plan.

Passing this gate proves only that the revision followed the declared control. It does not prove the model was correct, the facility condition existed, the action succeeded or the architecture meets every policy or legal requirement.
