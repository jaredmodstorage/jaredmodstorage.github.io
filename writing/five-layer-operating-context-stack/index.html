The Five-Layer Operating Context Stack for Multi-Facility AI

Identity, authority, state, time, and evidence should be assembled before an AI-assisted workflow is allowed to govern work across facilities.

By Jared Mastroianni13 min read

An AI system can produce a fluent answer with almost no operating context. That is the problem.

In a multi-facility operation, the same sentence can be correct for one location, prohibited at another, stale by the time it reaches a third, and outside the authority of the person asking. A model can recognize a maintenance note without knowing which facility it belongs to. It can recommend an action without knowing whether that action is allowed. It can summarize a status without knowing whether the source is current. It can cite an event without knowing whether the event was delivered, accepted, executed, or reconciled.

The remedy is not a longer prompt. It is an operating context stack.

This article proposes five layers that should be assembled before an AI-assisted workflow is allowed to govern work across facilities:

  1. identity context;
  2. policy and authority context;
  3. operational state context;
  4. event and temporal context; and
  5. decision and evidence context.

The stack is a reference model, not a product diagram. It does not describe a released Facily OS architecture, a modSTORAGE production system, a vendor integration, or a measured result.

Context is a governed input, not prompt decoration

“Add context” is often treated as a retrieval problem: find more documents, place them near the prompt, and let the model synthesize. That can improve relevance. It does not establish authority.

Operating context must answer harder questions:

  • Which real entity does this request concern?
  • Which role is acting, and within what scope?
  • Which policy version is effective?
  • Which source governs each state field?
  • When did the underlying occurrence happen?
  • When was it observed by this system?
  • What conflict or missing-data condition is active?
  • What evidence supports the recommendation?
  • Who approved the action?
  • What receipt and reconciliation prove the final state?

These questions belong in explicit fields with owners, timestamps, versions, and failure behavior. They should not depend on a model inferring the answer from prose.

The five layers are ordered. A higher layer may reference a lower one, but it must not silently redefine it. A recommendation cannot invent the facility identity. An event cannot grant authority. A current-looking state cannot override policy. A human approval cannot erase the evidence trail that made the decision reviewable.

Layer 1: identity context

Identity context establishes what and who the workflow is about.

At minimum, record:

  • stable facility ID;
  • current facility label and lifecycle state;
  • system or tenant boundary;
  • actor ID and authenticated role;
  • permitted facility, region, and portfolio scope;
  • service or automation identity when software is acting; and
  • the identifier translation used when two systems name the same entity differently.

The stable identifier matters more than the display name. Names change. Addresses can be formatted several ways. A legacy source may retain an old label. A platform login may administer an asset without establishing legal ownership, employment, operation, or provider status.

Identity context must preserve those boundaries. “Can access this record” and “owns this facility” are different propositions. “Runs this workflow” and “is the authoritative source” are different propositions. The stack should carry only the relationship needed for the decision and should name the evidence for that relationship.

Failure behavior: if facility identity, actor identity, or scope is ambiguous, stop before policy evaluation. Do not let the model choose the closest name.

Layer 2: policy and authority context

Policy context defines what may happen, who may decide, and where enforcement occurs.

Record:

  • policy ID, version, owner, and effective time;
  • permitted and prohibited actions;
  • consequence class;
  • thresholds for human review;
  • required approver role;
  • separation-of-duties rules;
  • enforcement point;
  • exception and expiration behavior; and
  • the rollback authority.

This layer separates a policy decision from policy enforcement. A rule engine, application service, or human reviewer may decide that an action is allowed. A different component may enforce the result. Both steps need identifiers and evidence.

NIST Special Publication 800-207 describes policy decision and enforcement concepts for zero-trust access architecture. That is a useful architectural distinction, but its scope is cybersecurity and access to enterprise resources. It does not define self-storage operating authority, employment roles, customer permissions, or the five-layer model proposed here.

Failure behavior: if the policy is missing, expired, conflicted, or outside the actor’s scope, route to an accountable human owner. “No rule found” must never become “allowed.”

Layer 3: operational state context

State context describes what is currently believed to be true and why.

For every state field used in a decision, record:

  • field definition and allowed values;
  • governing source and source owner;
  • observed value;
  • observation time;
  • freshness threshold;
  • transformation or projection version;
  • conflict state;
  • null behavior; and
  • last reconciled reference.

A dashboard is not automatically the source of truth. Neither is the newest record, the largest database, or the system with the cleanest interface. A derived state should identify the records and rules that produced it.

Multi-facility systems also need explicit partitioning. A portfolio-wide view must not blend fields whose meanings, timezones, source owners, or update rhythms differ. open, for example, may mean assigned in one system, unverified completion in another, and an unresolved exception in a third.

Failure behavior: stale, missing, or conflicting state remains visible as stale, missing, or conflicting. The model may explain the condition. It must not manufacture a clean state to keep the workflow moving.

Layer 4: event and temporal context

State answers “what is believed now.” Event context answers “what happened, according to whom, and when.”

Record:

  • event ID;
  • event type and schema version;
  • producer or source;
  • subject;
  • occurrence time;
  • ingestion time;
  • correlation or causation reference;
  • payload sensitivity class;
  • delivery and processing receipts; and
  • supersession or replay status.

Occurrence time and ingestion time are separate. A late-arriving event can be newer in the queue while describing an older occurrence. A repeated delivery may carry the same occurrence. A transport receipt proves that a message reached a boundary; it does not prove that the intended business action was authorized, executed, or reconciled.

CloudEvents provides a vendor-neutral format for event metadata. Its released core line is v1.0.2, while the repository’s main specification is work in progress. CloudEvents improves event interoperability; it does not define business authority, a processing model, delivery guarantees, or operating completion. Its specification also warns against placing sensitive information in context attributes.

Failure behavior: unknown schemas, impossible time order, duplicate identifiers, missing correlation, or sensitive context leakage should create an exception rather than a guessed timeline.

Layer 5: decision and evidence context

This layer makes the AI-assisted decision reconstructable.

Record:

  • decision ID and intended decision;
  • model, system, prompt, retrieval, and rule versions;
  • evidence references and their observation times;
  • assumptions and limitations;
  • recommendation and confidence language;
  • human reviewer and adjudication;
  • policy decision reference;
  • action request and acceptance receipt;
  • execution evidence;
  • reconciliation evidence; and
  • rollback owner and method.

W3C PROV-O offers a general ontology for entities, activities, agents, and derivations. It can help represent where decision evidence came from. It does not decide whether a source is operationally authoritative, whether an action is allowed, or whether a self-storage workflow is complete.

NIST AI RMF 1.0 organizes voluntary AI risk management through Govern, Map, Measure, and Manage. NIST’s current AI RMF page says version 1.0 is being revised. NIST AI 600-1 is a cross-sectoral generative-AI profile published July 26, 2024. These resources support risk identification, documentation, measurement, and human oversight; they do not prescribe this stack or certify an implementation.

Failure behavior: if the evidence packet cannot be reconstructed, the system may offer an informational summary but must not present the result as an authorized operating decision.

The context envelope

The five layers should be assembled into a versioned context envelope for one decision or workflow instance. The envelope is not a copy of every record. It is the minimum evidence-bearing snapshot needed to evaluate, authorize, execute, and later audit the decision.

One envelope should declare:

  • its own version and creation time;
  • the decision or workflow instance it supports;
  • references to each layer;
  • the rule for resolving conflicts between layers;
  • sensitivity and retention controls;
  • a hash or immutable reference when consequence warrants it; and
  • the exact point at which the envelope expires and must be rebuilt.

Do not propagate the full envelope everywhere. OpenTelemetry Baggage is one mechanism for carrying application-defined context through a distributed request. Its API is stable, but baggage can cross process boundaries, may be visible in network headers, and has no built-in integrity guarantee. Use opaque references where possible. Keep secrets, customer data, and sensitive policy facts out of broadly propagated context.

A fictional multi-facility incident

Consider a fictional workflow. It does not describe a real facility, vendor, integration, or result.

An AI assistant receives three signals associated with a demonstration facility: a manager report that a gate is intermittently failing, a stale device heartbeat, and an open maintenance item. The assistant is asked what to do next.

The five-layer envelope could contain:

Identity. FAC-DEMO-014 is the stable facility ID. The requesting actor is a regional operations reviewer scoped to the demonstration region. The device and work-order systems both map to that facility through approved translation records.

Policy. Policy ACCESS-INCIDENT-02, version 4, permits the assistant to summarize and recommend. It prohibits automated unlock or access-rule changes. A safety- or access-impacting incident requires named human review. The application service is the enforcement point.

State. The incident is open in the governing work-order source. The heartbeat is outside its freshness threshold. No verified closure evidence exists. The visible state is therefore open_with_stale_telemetry, not device_failed and not resolved.

Events. The manager report occurred before the last heartbeat but was ingested after it. Both occurrence and ingestion times are retained. The maintenance-created event and telemetry event have separate IDs and share a correlation reference. Message delivery is recorded without being labeled execution.

Decision and evidence. The assistant recommends an onsite inspection and a controlled vendor-dispatch review. It states that the heartbeat alone does not prove physical failure. A named reviewer approves dispatch but does not authorize an unlock. The accepted work-order receipt is recorded. Closure remains blocked until verification evidence is attached and reconciled to the stable facility ID.

Without the stack, the same signals could produce a confident but unsafe shortcut: “The gate is down; unlock it remotely and close the ticket.” The stack changes the question from “What does the model think?” to “What can this workflow support, authorize, and prove?”

Five omission tests

Use these tests during design review:

  1. Identity omission: Could the same request be routed to the wrong facility or acted on by the wrong scope?
  2. Policy omission: Could a recommendation be mistaken for permission?
  3. State omission: Could stale, conflicting, or derived data appear current and authoritative?
  4. Event omission: Could delivery be mistaken for occurrence, execution, or completion?
  5. Evidence omission: Could the result be impossible to reconstruct, challenge, or roll back?

If any answer is yes, the workflow is not ready for consequential automation.

Interface requirements

The operator should not have to inspect raw JSON to understand the stack. The interface should show:

  • facility and actor scope;
  • effective policy and required reviewer;
  • state source and freshness;
  • event occurrence versus observation time;
  • unresolved conflicts;
  • evidence used and evidence withheld;
  • recommendation versus authorized action;
  • receipt, reconciliation, and rollback state; and
  • a clear stop or hand-back-control path.

Every visible action should either work within the declared authority or be removed. Disabled controls should explain the missing layer. A mobile operator should see the same decision boundary as a desktop operator, even if the presentation is condensed.

A 45-field architecture exercise

Choose one consequential but bounded workflow. Download the operating-context-stack worksheet and complete one row.

Then run a tabletop with an operator, a source owner, and a technical reviewer:

  1. Remove one identity field. Can the workflow still prove the entity and scope?
  2. Expire the policy. Does the system stop?
  3. Make the governing state stale. Does the interface show the condition?
  4. Deliver an older event late. Does the timeline stay truthful?
  5. Withhold the reconciliation evidence. Does the workflow refuse to call the action complete?
  6. Replace the human reviewer with a role outside scope. Does enforcement reject the decision?
  7. Rebuild the context envelope. Can another reviewer reach the same bounded conclusion?

The purpose is not to make every field mandatory in every workflow. The purpose is to force an explicit decision about what is required, who owns it, and what happens when it is absent.

Release gate

Before the workflow governs work, verify:

  • all five layers have named owners;
  • stable IDs and translations are tested;
  • policy versions and effective times are machine-readable;
  • missing policy defaults to stop;
  • governing state sources and freshness thresholds are explicit;
  • occurrence and ingestion times are separate;
  • schemas and transformations are versioned;
  • context propagation excludes sensitive values;
  • human review triggers are consequence-based;
  • action receipts are distinct from execution and reconciliation;
  • rollback is owned and exercised in proportion to risk;
  • fictional tests cover stale, duplicate, conflicting, and out-of-scope inputs;
  • desktop and narrow-screen interfaces preserve the decision boundary; and
  • documentation names the standards used and their limitations.

Sources and limitations

Observed August 22, 2026:

  • NIST AI RMF 1.0, published January 26, 2023; NIST’s current program page says version 1.0 is being revised.
  • NIST AI 600-1, Generative AI Profile, published July 26, 2024 and updated April 8, 2026.
  • NIST SP 800-207, Zero Trust Architecture, final August 11, 2020.
  • CloudEvents specification repository, listing v1.0.2 as the latest released core specification and the main line as work in progress.
  • W3C PROV-O, a W3C Recommendation dated April 30, 2013.
  • OpenTelemetry Baggage API, currently marked Stable.

These sources inform parts of the model; none defines this five-layer stack or a self-storage industry standard. NIST AI resources are voluntary and cross-sectoral. SP 800-207 addresses cybersecurity and enterprise-resource access. CloudEvents addresses event interoperability, not business authority or delivery guarantees. PROV-O is a general provenance ontology. OpenTelemetry Baggage is a propagation mechanism, not an authorization or integrity control.
